- **`md.legacy.pos.order`: 33,725 registros de origen desconocido.** La BD tiene 84,839 registros pero los scripts versionados en `/opt/legacy_migration/` solo explican 51,114 (`legacy_ref='MICROSIP-PV-*'`). Los otros 33,725 (`legacy_ref='POS-*'`, con montos reales) fueron cargados el mismo día por un script que **no quedó en el repositorio**. Esto es un riesgo de auditoría contable: no se puede reproducir ni verificar ese origen.
- **Catálogo `product.template`: 100% de los códigos `MICROSIP-*` están archivados.** De 5364 creados, sobreviven 2692, todos con `active=False`. Hubo una deduplicación manual sin script versionado — el criterio de limpieza no está documentado.

## 4. Estrategia ETL Asistida por Ollama / Ollama-Assisted ETL Strategy

Flujo propuesto, consistente con el patrón ya usado en `/opt/legacy_migration/etl_migration.py` (extracción vía consulta directa → transformación → `xmlrpc.client`):

```
[Fuente: Firebird .FDB / CSV export Odoo.sh]
        ↓
[1. Extracción determinística en Python — sin IA]
        ↓  (fragmento JSON/CSV, <2K tokens por lote)
[2. Prompt a Ollama (qwen2.5-coder:7b) — genera/valida script de transformación]
        ↓
[3. Script Python revisado por humano antes de ejecutar]
        ↓
[4. Carga vía xmlrpc.client a Odoo 19 Community]
        ↓
[5. Verificación: conteo BD vs. conteo esperado (como en Hallazgo 1 de MIGRATION_NOTES.md)]
```

**Regla operativa nueva (gobernanza) / New operating rule (governance):**
Todo script generado o ejecutado por Ollama contra datos reales debe **commitearse en el repositorio antes de ejecutar**, junto con el prompt que lo generó. Motivo: la carga de 33,725 registros `POS-*` (§8.1) fue ejecutada por un agente sin dejar script versionado, haciéndola irreproducible y no auditable hoy. No se repite ese patrón.
Every script generated or run by Ollama against real data must be **committed to the repo before execution**, together with the prompt that generated it. Reason: the 33,725 `POS-*` records (§8.1) were loaded by an agent with no versioned script, making it unreproducible and unauditable today. This pattern must not recur.

**Regla no negociable para prompts de inventario / Non-negotiable rule for inventory prompts:**
Cualquier prompt a Ollama que toque `stock.quant`, cantidades físicas, o endpoints de lectura de existencias **debe usar exclusivamente el término 'A la mano' (On Hand)**. Nunca "Disponible", "Stock" ni "Existencias" — esta regla ya está codificada en el propio repo (`custom_shop_qty_selector/README.md`, campo `cantidad_la_mano` en `md_lots_management`) y se hereda tal cual.

Plantilla de prompt de ejemplo:
```
Rol: Ingeniero ETL Odoo 19.
Tarea: generar función Python que use xmlrpc.client para leer la cantidad
'A la mano' (On Hand) de stock.quant para una lista de product_id.
Restricción de nomenclatura: la variable, el docstring y cualquier log
deben decir 'a_la_mano' / 'On Hand'. Prohibido usar 'disponible',
'stock' o 'existencias' en cualquier identificador o texto generado.
Input: [fragmento CSV/JSON de hasta N filas]
Output: función Python documentada + manejo de errores xmlrpc.Fault.
```

**Prioridad de aplicación (según cuellos de botella §2.1):**
1. Investigar origen de los 33,725 registros `POS-*` (comparar estructura contra los 51,114 conocidos, usando Ollama para generar el script de diffing).
2. Generar script de verificación de integridad `product.template` archivado vs. catálogo vivo.
3. Solo después, evaluar migración de las 5 sucursales restantes (bloqueado hasta confirmar fuentes Firebird).

## 5. Headless Translation (Next.js/React) / Headless Translation Strategy

Dado que no existe base previa, el plan es incremental:

1. **Inventario asistido por Ollama de vistas Odoo a migrar** — usar el `.graphify/GRAPH_REPORT.md` existente (ya mapea 3257 nodos/5216 edges del repo) como insumo para que Ollama priorice qué vistas XML tienen mayor "conectividad" (más reutilizadas) y deberían traducirse primero a componentes React.
2. **Diseño de endpoints REST/JSON-RPC** desde los controllers ya existentes en `medicine_depot_portal/controllers/` y `medicine_depot_website/controllers/api.py` como base — no partir de cero, son la capa headless embrionaria.
3. **Endpoint de cantidades:** cualquier endpoint nuevo para Next.js que exponga cantidades físicas debe nombrarse y documentarse con 'A la mano' (On Hand) — ej. `GET /api/product/{id}/on-hand`, nunca `/stock` o `/available`.
4. **Seguridad primero:** antes de exponer cualquier endpoint headless de escritura, cerrar el hallazgo §2.3 (`/afiliacion` sudo público) como patrón a NO repetir en la nueva capa API.

## 10. Fase 1 Ejecutada — Seguridad `/afiliacion` (2026-07-27)

**Alcance:** cerrar los hallazgos abiertos de `AFILIACION_WORKFLOW_AUDIT.md` (§2.3) y verificar higiene de `admin_passwd` (§2.5).

1. **Auditoría re-verificada contra código real** (no solo contra el `.md`, que estaba desactualizado desde el commit baseline `9ca60a9`). Documento `AFILIACION_WORKFLOW_AUDIT.md` corregido en el repo: 4 hallazgos marcados como ya resueltos con evidencia de línea de código, 2 marcados como confirmados-abiertos.
2. **Rate limiting implementado** en `controllers/portal.py` (`_is_affiliation_rate_limited`): máximo 5 intentos POST por IP cada 15 minutos, respuesta `429` con mensaje claro. Limitación conocida y documentada en el propio código: el contador es en memoria por worker (no persistente/no compartido entre los 5 workers de `odoo.conf`), así que es una primera barrera, no reemplazo de reCAPTCHA/WAF. Follow-up recomendado: versión persistente (DB-backed) si el spam real lo justifica.
3. **Auditoría de consentimiento agregada**: cada afiliación exitosa deja un log estructurado (`partner_id`, `email`, IP, User-Agent, timestamp) confirmando que `privacy` fue aceptado. Es evidencia en logs, no en base de datos — persistencia en modelo dedicado queda como follow-up si se requiere valor probatorio legal más fuerte.
4. **`admin_passwd`: verificado, no se tocó.** Ya estaba rotado y fuera de git tracking desde el 2026-07-24 (commit de merge). El valor débil histórico (`admin`) sigue visible en el historial de git (commit `b41d3f3`) pero ya no es el valor activo — ver pregunta abierta §8 sobre si purgar el historial.
5. **Prueba real contra el contenedor `dev` (2026-07-27, tras reiniciar `odoo`):**
   - ✅ Validación backend: confirmada (`400` con mensajes claros).
   - ✅ Log de consentimiento: confirmado, línea real capturada en los logs de Odoo con `partner_id`, email, IP y user-agent.
   - ❌ **Rate limiting: NO funciona en este entorno.** 6 requests consecutivos, el 6to no fue bloqueado. Causa confirmada en logs: `odoo.conf` tiene `workers = 5`, y los 6 requests se repartieron entre 3 procesos worker distintos (PIDs 19, 21, 14); cada worker tiene su propio contador en memoria (`_affiliation_attempts_by_ip` es un atributo de clase, pero cada proceso worker tiene su propia copia en memoria — no hay memoria compartida entre procesos), así que ninguno acumuló 5 intentos. La limitación documentada en el código no era teórica: es la causa raíz confirmada.
   - Se limpió el `res.partner` de prueba creado durante la validación (`id=7459`) tras confirmar el nombre antes de `unlink()`.
   - **Conclusión: el rate limiter en memoria era efectivamente inefectivo en cualquier despliegue con `workers > 1`.** Decisión del usuario: implementar versión DB-backed.

### Fase 1.1 — Rate limit persistente (DB-backed), 2026-07-27

1. **Modelo nuevo:** `medicine.depot.affiliation.attempt` (`models/affiliation_rate_limit.py`) — un solo campo `ip_address` + `create_date` nativo. Cron diario `_gc_old_attempts()` purga registros de más de 24h (`data/affiliation_rate_limit_cron.xml`).
2. **Controlador reescrito:** `_is_affiliation_rate_limited` ahora cuenta con `search_count` sobre la tabla en Postgres en vez de un dict en memoria — compartido por los 5 workers.
3. **Módulo actualizado en `dev`:** `odoo -u medicine_depot_portal --stop-after-init` contra el contenedor corriendo (con `--no-http` para no chocar con el puerto del proceso principal). Se verificó por `psql` que la tabla, los campos, el ACL y el cron se crearon correctamente.
4. **Reprueba real, contenedor reiniciado con `workers=5`:**
   - 6 POST consecutivos → intentos 1–5: `400` (validación); intento 6: **`429`** ✅.
   - Logs confirman que los 6 requests se repartieron entre 3 workers distintos (PID 14, 18, 17) — el límite se sostuvo *a pesar de* estar en distintos procesos, a diferencia de la versión en memoria.
   - `SELECT ... GROUP BY ip_address` en la tabla real: exactamente 5 filas (el intento bloqueado no se contó de más).
   - Un 7mo intento, con sesión/cookie nueva de curl, también dio `429` — confirma persistencia real, no solo suerte de reparto de workers.
   - Se limpiaron las filas de prueba de la tabla después de verificar.
5. **Estado: rate limiting real y verificado en `dev`.** Sigue siendo una barrera básica (no reCAPTCHA/WAF) pero ahora sí cumple lo que promete.

### 12.1 — `test_23`: pregunta de arquitectura, no bug (sin resolver)

`production_lot.py` fuerza **todo** `stock.lot` a `company_id=False` (lote "global") sin importar la compañía del producto (`_md_normalize_lot_company_vals`, línea 279-281) — diseño intencional, probado en 6 escenarios distintos (tests 22-27: "un producto global crea lote global", "un producto de compañía también crea lote global", etc.).

`test_23` crea un **producto con `company_id` de una compañía específica** y espera que su lote siga siendo global. Falla con:
```
UserError: "LOT-2026-023" belongs to company "" while "Product" belongs to another company.
```
Leyendo el docstring de `_check_company()` en el core de Odoo: un registro con `company_id=False` (global) solo puede referenciar registros relacionados que **también** sean `company_id=False` o pertenezcan a la misma compañía. Un lote global (`company_id=False`) que apunta a un producto **de una compañía específica** es, según esta regla, una inconsistencia real de integridad multi-compañía — no un falso positivo de Odoo.

**Esto es relevante para la migración real de MedicineDepot** (6 sucursales, posible multi-compañía a futuro): si en algún momento los productos se vuelven específicos de sucursal/compañía, la regla actual de "todos los lotes son siempre globales" dejará de ser válida para Odoo, y cualquier intento de crear/actualizar esos lotes lanzará este mismo `UserError` en producción, no solo en tests.

**No se tocó el código de producción** (`_md_normalize_lot_company_vals`) porque cambiar esa regla afecta el comportamiento real de trazabilidad de lotes entre sucursales — es una decisión de negocio, no un bug a corregir por iniciativa propia. Opciones para decidir:
- **(a)** ¿Los productos de MedicineDepot son y seguirán siendo globales (sin `company_id` propio)? Si es así, `test_23` prueba un escenario que nunca ocurre en la realidad — se puede simplemente eliminar o marcar como no aplicable.
- **(b)** ¿Se planea que los productos sean específicos de sucursal/compañía en algún momento? Si es así, hay que decidir si los lotes deben *seguir* la compañía del producto (rediseño de `_md_normalize_lot_company_vals`) en vez de forzarse siempre a global — un cambio de diseño real, no cosmético.
