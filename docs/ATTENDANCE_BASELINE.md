### Modelo 1: `hr.attendance.authorized.ip` (nuevo) / Model 1 (new)

```python
# custom_addons/hr_attendance_ip_autologin/models/hr_attendance_authorized_ip.py
import ipaddress

from odoo import api, fields, models
from odoo.exceptions import ValidationError


class HrAttendanceAuthorizedIp(models.Model):
    _name = "hr.attendance.authorized.ip"
    _description = "IP autorizada para check-in automatico por sucursal / Authorized IP for branch auto check-in"

    name = fields.Char(required=True, help="Ej. 'Router principal - MDS Cancun'")
    company_id = fields.Many2one(
        "res.company", required=True, index=True, default=lambda self: self.env.company,
        help="Sucursal a la que pertenece esta IP (1 res.company = 1 sucursal en esta instancia).",
    )
    ip_address = fields.Char(
        required=True,
        help="IP unica (189.203.10.5) o rango CIDR (189.203.10.0/24).",
    )
    active = fields.Boolean(default=True)

    @api.constrains("ip_address")
    def _check_ip_address(self):
        for rec in self:
            try:
                ipaddress.ip_network(rec.ip_address, strict=False)
            except ValueError as exc:
                raise ValidationError(
                    f"'{rec.ip_address}' no es una IP ni un rango CIDR valido."
                ) from exc

    def _matches(self, remote_ip):
        """True si remote_ip cae dentro de este registro (IP unica o CIDR)."""
        try:
            network = ipaddress.ip_network(self.ip_address, strict=False)
            return ipaddress.ip_address(remote_ip) in network
        except ValueError:
            return False
```

### Punto de intercepción del login / Login interception point

Sobrescribir `res.users.authenticate` es frágil: en Odoo 19 hay múltiples
rutas de autenticación (password, OAuth/SSO, 2FA, API keys) y no todas pasan
por el mismo método. El punto estable y suficiente para el caso de uso
("cuando el empleado abre sesión en el navegador desde la sucursal") es el
controlador `web.Home.web_login`, heredado — se ejecuta una sola vez por
login interactivo, después de que Odoo ya confirmó la sesión (`request.session.uid`
seteado). / Overriding `res.users.authenticate` is fragile: Odoo 19 has
multiple auth paths (password, OAuth/SSO, 2FA, API keys) and not all of them
go through the same method. The stable, sufficient interception point for
this use case ("when the employee opens a browser session from the branch")
is the inherited `web.Home.web_login` controller — it runs exactly once per
interactive login, after Odoo has already confirmed the session
(`request.session.uid` set).

```python
# custom_addons/hr_attendance_ip_autologin/controllers/main.py
import logging

from odoo import http
from odoo.http import request
from odoo.addons.web.controllers.home import Home

_logger = logging.getLogger(__name__)


class HomeIPAutoCheckin(Home):

    @http.route()
    def web_login(self, redirect=None, **kw):
        response = super().web_login(redirect=redirect, **kw)

        # Solo actuar si el login fue exitoso (uid seteado en la sesion).
        # Only act if the login actually succeeded (uid set on the session).
        if request.session.uid:
            try:
                request.env["hr.employee"].sudo()._auto_checkin_by_ip(
                    request.session.uid, request.httprequest.remote_addr
                )
            except Exception:  # nunca bloquear el login por esto / never block login over this
                _logger.exception("hr_attendance_ip_autologin: fallo el intento de auto check-in")

        return response
```

### Lógica de negocio / Business logic

```python
# custom_addons/hr_attendance_ip_autologin/models/hr_employee.py
from odoo import api, models


class HrEmployee(models.Model):
    _inherit = "hr.employee"

    @api.model
    def _auto_checkin_by_ip(self, user_id, remote_ip):
        employee = self.search([("user_id", "=", user_id)], limit=1)
        if not employee or not employee.company_id:
            return False

        authorized_ips = employee.company_id.attendance_authorized_ip_ids.filtered("active")
        if not any(rec._matches(remote_ip) for rec in authorized_ips):
            return False

        # No duplicar: solo marcar entrada si el empleado esta actualmente
        # afuera (sin un check-in abierto).
        # Don't duplicate: only mark check-in if the employee currently has
        # no open attendance.
        if employee.attendance_state == "checked_out":
            employee._attendance_action_change()
            return True
        return False
```

### Riesgos y decisiones abiertas / Risks and open decisions

- **Falsos positivos en redes compartidas / False positives on shared
  networks:** si una sucursal usa NAT con una sola IP pública, cualquier
  dispositivo en esa red (celular personal por WiFi de invitados, por
  ejemplo) dispararía el check-in al hacer login. Mitigación propuesta:
  restringir el auto check-in a rangos CIDR internos específicos (LAN de
  oficina), no a la IP pública completa, y dejarlo como algo que el
  encargado de sucursal configura explícitamente. / If a branch uses NAT
  with a single public IP, any device on that network (a personal phone on
  guest WiFi, say) would trigger check-in on login. Proposed mitigation:
  restrict auto check-in to specific internal CIDR ranges (office LAN), not
  the whole public IP, left as something the branch manager configures
  explicitly.
- **No reemplaza el Quiosco / Does not replace the Kiosk:** este mecanismo es
  un complemento para asistencia vía backend (`attendance_from_systray`),
  no un reemplazo del modo Quiosco existente — ambos pueden convivir.
- **Extensión futura a almacén (fuera de alcance aquí) / Future extension to
  warehouse (out of scope here):** si más adelante se quisiera reusar este
  mismo patrón de IPs-por-sucursal para restringir *operaciones de almacén*
  (por ejemplo, permitir ajustes de cantidad **a la mano** solo desde la IP
  de la sucursal correspondiente), el modelo `hr.attendance.authorized.ip`
  se podría generalizar a `res.company` en vez de vivir en este módulo de
  RRHH — pero eso es una decisión de diseño separada, no parte de este
  entregable. / If this same per-branch IP pattern were later reused to
  restrict *warehouse operations* (e.g. only allowing **on hand** quantity
  adjustments from the matching branch's IP), the
  `hr.attendance.authorized.ip` model could be generalized off `res.company`
  instead of living in this HR module — but that's a separate design
  decision, not part of this deliverable.
